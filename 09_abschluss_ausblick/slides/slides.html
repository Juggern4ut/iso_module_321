Lektion 09: Abschluss & Ausblick

Von 0 auf Cloud – Die Evolution einer Anwendung

Lernziele

  • Ich kann erklären, warum verteilte Systeme überhaupt entstanden sind.
  • Ich kann beschreiben, welches Problem jede Entwicklungsstufe löst.
  • Ich kann die im Modul behandelten Technologien den passenden Stufen zuordnen.
  • Ich kann einschätzen, welchen Technologien ich später begegnen werde.
  • Ich kann begründen, warum Komplexität nur eingeführt werden soll, wenn sie ein reales Problem löst.

Eine Anwendung wächst

Wir verfolgen eine einzige Anwendung über acht Entwicklungsstufen – vom Studentenprojekt bis zum Cloud-nativen System.

Roter Faden

  • Jede Stufe entsteht, weil die vorherige ein Problem nicht mehr lösen kann.
  • Jede Lösung bringt neue Vorteile – und ein neues Problem.
  • Viele Technologien aus diesem Modul tauchen genau hier wieder auf.

Worauf wir achten

  • Welches Problem löst diese Stufe?
  • Welche neuen Vorteile entstehen?
  • Welches neue Problem entsteht dadurch?

Letzte Diskussionsfrage

Wenn ihr heute eine neue Anwendung entwickeln würdet – bei welcher Stufe würdet ihr beginnen?

Erkenntnis

Nicht jede Anwendung braucht Kubernetes, Kafka und 20 Microservices.

Komplexität nur dann einführen, wenn sie ein reales Problem löst.

Merksätze

  • Jede Entwicklungsstufe löst ein konkretes Problem der vorherigen Stufe.
  • Mehr Technologie bedeutet auch mehr Betriebsaufwand und Komplexität.
  • Die Bausteine aus diesem Modul – Protokolle, Schnittstellen, Container, Systemkomponenten – fügen sich hier zu einem Gesamtbild zusammen.
  • Architekturentscheidungen sollten sich am realen Problem orientieren, nicht am Trend.
  • Verteilte Systeme sind kein Selbstzweck, sondern eine Antwort auf wachsende Anforderungen.

Wichtiger Praxispunkt: Beginnt einfach – und baut Komplexität erst aus, wenn sie gebraucht wird.
