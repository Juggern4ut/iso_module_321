Lektion 08: Protokolle und Schnittstellen

Daten austauschen über wohl definierte Schnittstellen

Lernziele

  • Ich kann erklären, was ein Protokoll ist und wozu TCP und HTTP dienen.
  • Ich kann REST, GraphQL, gRPC und WebSockets voneinander unterscheiden.
  • Ich kann erklären, was ein Gateway und ein Proxy sind.
  • Ich kann für ein gegebenes Szenario eine passende Schnittstelle auswählen.
  • Ich kann begründen, warum klar definierte Schnittstellen in verteilten Systemen wichtig sind.

Was ist ein Protokoll?

Ein Protokoll ist eine Vereinbarung, wie zwei Parteien miteinander kommunizieren: welche Nachrichten erlaubt sind, in welcher Reihenfolge sie gesendet werden und was sie bedeuten.

Warum Protokolle?

  • Erlaubt dass Systeme miteinander sprechen können.
  • Protokolle definieren: Format, Reihenfolge, Fehlerbehandlung.
  • Ermöglichen, dass verschiedene Systeme zusammenarbeiten.

Schichtenmodell

  • Protokolle bauen aufeinander auf.
  • HTTP baut auf TCP auf.
  • TCP baut auf IP auf.
  • Jede Schicht erfüllt eine andere Aufgabe.

TCP – Das Fundament

TCP (Transmission Control Protocol) ist ein verbindungsorientiertes Protokoll, das eine zuverlässige und geordnete Datenübertragung garantiert.

Eigenschaften

  • Verbindungsaufbau vor dem Datentransfer
  • Pakete kommen in der richtigen Reihenfolge an
  • Verlorene Pakete werden automatisch wiederholt
  • Flusskontrolle verhindert Überlastung

Wann TCP?

  • Wenn Datenverlust nicht akzeptabel ist
  • Webseiten, Dateiübertragung, E-Mail, APIs
  • UDP wäre z. B. bei Videokonferenzen sinnvoller

HTTP – Das Web-Protokoll

HTTP (Hypertext Transfer Protocol) baut auf TCP auf und definiert, wie Client und Server Nachrichten austauschen: Anfrage und Antwort.

HTTP-Methoden

  • GET – Daten lesen
  • POST – Daten erstellen
  • PUT / PATCH – Daten ändern
  • DELETE – Daten löschen

Status-Codes

  • 200 OK – Erfolg
  • 201 Created – Erstellt
  • 400 Bad Request – Fehlerhafte Anfrage
  • 401 Unauthorized – Nicht authentifiziert
  • 404 Not Found – Nicht gefunden
  • 500 Server Error – Serverfehler

Was ist eine Schnittstelle?

Eine Schnittstelle (API – Application Programming Interface) legt fest, wie andere Systeme oder Komponenten mit einem Dienst kommunizieren können.

Warum wohl definiert?

  • Klare Verträge zwischen Diensten
  • Änderungen sind beherrschbar
  • Fehler lassen sich gezielt eingrenzen
  • Mehrere Clients können dieselbe Schnittstelle nutzen

Was gehört dazu?

  • Endpunkte oder Operationen
  • Datenformate (z. B. JSON, Protobuf)
  • Fehlerbehandlung
  • Versionierung

REST

REST (Representational State Transfer) ist ein Architekturstil, der HTTP-Methoden und Ressourcen-URLs nutzt, um Daten auszutauschen.

Merkmale

  • Ressourcen-orientiert: /users/42
  • Stateless – jede Anfrage ist unabhängig
  • JSON als gängiges Datenformat
  • Einfach und weitverbreitet

Beispiel

GET /api/users/42

→ 200 OK
{
  "id": 42,
  "name": "Anna"
}

Typisch: Web-APIs, CRUD-Operationen

GraphQL

GraphQL ist eine Abfragesprache für APIs, bei der der Client genau festlegt, welche Daten er benötigt – über einen einzigen Endpunkt.

Merkmale

  • Ein einziger Endpunkt: /graphql
  • Client bestimmt die Datenstruktur
  • Kein Over- oder Underfetching
  • Schema definiert alle Möglichkeiten

Beispiel

query {
  user(id: 42) {
    name
    email
  }
}

Typisch: Mobile Apps, komplexe Datenmodelle

gRPC

gRPC ist ein Framework, das auf HTTP/2 und binären Protokoll-Puffern (Protobuf) basiert und besonders schnelle Kommunikation zwischen Diensten ermöglicht.

Merkmale

  • Schnell und effizient (binäres Format)
  • Typsicheres Schema (Protobuf)
  • Bidirektionales Streaming möglich
  • Code wird automatisch generiert

Beispiel

rpc GetUser (UserRequest)
    returns (UserResponse);

message UserRequest {
  int32 id = 1;
}

Typisch: Microservice-Kommunikation intern

WebSockets

WebSockets ermöglichen eine dauerhafte, bidirektionale Verbindung zwischen Client und Server – beide Seiten können jederzeit Nachrichten senden.

Merkmale

  • Verbindung bleibt nach dem Aufbau offen
  • Nachrichten können in beide Richtungen fliessen
  • Kein wiederholtes Polling nötig
  • Sehr niedrige Latenz

Typische Verwendung

  • Chat-Anwendungen
  • Live-Daten (Börsenkurse, Sport)
  • Echtzeit-Kollaboration
  • Push-Benachrichtigungen

Gateway

Ein API-Gateway ist ein einzelner Eintrittspunkt für alle eingehenden Anfragen. Es übernimmt Querschnittsaufgaben und leitet Anfragen an die richtigen Dienste weiter.

Typische Aufgaben

  • Anfragen an den richtigen Dienst weiterleiten
  • Authentifizierung und Autorisierung prüfen
  • Rate Limiting
  • Logging und Monitoring
  • SSL-Terminierung

Warum Gateway?

  • Clients kennen nur einen einzigen Zugangspunkt
  • Interne Dienste bleiben nach aussen verborgen
  • Sicherheitslogik ist zentral gesammelt
  • Flexibles Routing ohne Client-Änderungen

Proxy

Ein Proxy ist ein Vermittler zwischen Client und Server. Forward Proxy steht vor dem Client, Reverse Proxy steht vor dem Server.

Forward Proxy

  • Steht auf der Client-Seite
  • Leitet Anfragen im Namen des Clients weiter
  • Typisch: Firmennetzwerke, Anonymisierung
  • Der Server sieht den Proxy, nicht den echten Client

Reverse Proxy

  • Steht vor dem Server
  • Nimmt Anfragen entgegen und leitet weiter
  • Typisch: nginx, Caddy vor mehreren Servern
  • Kann SSL, Caching und Lastverteilung übernehmen

Vergleich der Schnittstellen

REST GraphQL gRPC WebSocket
Transport HTTP HTTP HTTP/2 WS (über HTTP)
Format JSON JSON Protobuf (binär) Beliebig
Kommunikation Request / Response Request / Response Streaming möglich Bidirektional
Stärke Einfachheit Flexibilität Performance Echtzeit
Typischer Einsatz Web-APIs Mobile Apps Microservices intern Live-Daten, Chat

Wann welche Schnittstelle?

REST
Öffentliche Web-API, einfache CRUD-Operationen, breite Kompatibilität
GraphQL
Mobile Apps, wechselnde Datenanforderungen, Aggregation mehrerer Quellen
gRPC
Interne Microservice-Kommunikation, hohe Performance, typsichere Verträge
WebSocket
Chat, Live-Updates, Echtzeit-Kollaboration
Gateway
Einheitlicher Zugangspunkt, viele interne Dienste, Sicherheit zentral
Proxy
SSL-Terminierung, Caching, Lastverteilung, Netzwerkkontrolle

Typische Fehlannahmen

  • REST ist nicht dasselbe wie HTTP – REST ist ein Architekturstil, der HTTP nutzt.
  • GraphQL ersetzt keine Datenbank – es ist nur eine Abfrageschicht.
  • gRPC ist nicht immer schneller – es kommt auf den Anwendungsfall an.
  • Ein Gateway ist kein Load Balancer, auch wenn sie Aufgaben teilen können.
  • WebSockets sind nicht für jede Echtzeitanforderung nötig.
  • Mehr Schnittstellen bedeuten nicht mehr Flexibilität – sie erhöhen die Komplexität.
Die beste Schnittstelle ist die, die zum konkreten Problem passt – nicht die neueste oder komplexeste.

Merksätze

  • Protokolle wie TCP und HTTP regeln, wie Daten transportiert werden.
  • Schnittstellen wie REST, GraphQL, gRPC und WebSocket regeln, was zwischen Diensten ausgetauscht wird.
  • Gateway und Proxy steuern den Zugang zu Schnittstellen, sind aber selbst keine Schnittstellen.
  • Gut definierte Schnittstellen machen verteilte Systeme beherrschbar.
  • Die passende Wahl hängt immer vom konkreten Anwendungsfall ab.

Wichtiger Praxispunkt: erst Kommunikationsmuster klären, dann Technologie auswählen.
