Lektion 2: Eigenschaften verteilter Systeme

Idempotenz, Retry, Resilience und Transaktionsgrenzen

Lernziele

  • Ich kann erklären, warum Netzwerke, Timeouts und Teilausfälle normale Fälle sind.
  • Ich kann Retry und Idempotenz fachlich korrekt zusammenbringen.
  • Ich kann Resilience als Entwurfsprinzip für verteilte Systeme beschreiben.
  • Ich kann erklären, warum klassische Transaktionen über mehrere Services problematisch sind.
  • Ich kenne sinnvolle Einsatzzwecke von Event Sourcing.

Warum diese Themen wichtig sind

Monolith denkt lokal

  • Funktionsaufruf ist schnell und direkt.
  • Eine Datenbanktransaktion deckt oft alles ab.
  • Fehler sind meist Exceptions im selben Prozess.

Warum diese Themen wichtig sind

Verteiltes System denkt unvollständig

  • Antworten können verspätet kommen oder ganz fehlen.
  • Eine Anfrage kann verarbeitet worden sein, obwohl der Client ein Timeout sieht.
  • Ein Teil des Systems kann ausfallen, während andere Teile weiterlaufen.

Standard in der Praxis: Systeme werden so gebaut, dass sie mit Unsicherheit umgehen, nicht so, als gäbe es sie nicht.

Zweiter Schwerpunkt: Wenn mehrere Services beteiligt sind, reichen klassische ACID-Transaktionen oft nicht mehr. Dann werden Muster wie CQRS und Event Sourcing relevant.

Retry ohne Idempotenz ist gefährlich

Beispiel: Ein Payment-Service erhält POST /payments.

  • Der Service belastet die Kreditkarte korrekt.
  • Die Antwort geht wegen eines Netzwerkfehlers verloren.
  • Der Client sieht ein Timeout und sendet dieselbe Anfrage nochmals.

Risiko: doppelte Zahlung, doppelte Bestellung, doppelte E-Mail, doppelte Buchung.

Idempotenz

Definition

Eine Operation ist idempotent, wenn mehrfache gleiche Ausführung denselben fachlichen Endzustand erzeugt wie eine einmalige Ausführung.


Praxis

  • PUT /users/42 mit demselben Inhalt ist meist idempotent.
  • POST /payments ist es ohne Zusatzmechanismus meist nicht.
  • Deshalb werden oft Idempotency Keys verwendet.

Praxisbeispiel: Idempotency Key

Client sendet Zahlung
Idempotency-Key: 8f3...
→
Service speichert Key + Ergebnis
erste Verarbeitung gewinnt
→
Bei Retry liefert Service dieselbe Antwort statt erneut zu buchen
  • Typisch bei Payments, Bestellungen, Ticketkäufen, Webhooks.
  • Wichtig ist die fachliche Eindeutigkeit: gleicher Key = gleiche Operation.
  • Der Key braucht meist eine begrenzte Lebensdauer und klare Speicherstrategie.

Retry richtig einsetzen

Situation Retry sinnvoll? Begründung
Timeout / temporärer Netzwerkfehler Ja Fehler kann flüchtig sein; Limits nötig.
Validierungsfehler / fachlich ungültige Daten Nein Der gleiche Request wird wieder scheitern.
Nicht idempotente Aktion ohne Schutz Nein Retry kann Schaden verdoppeln.

Resilience / Design for Failure

Resilience: System trotz Fehlern kontrolliert nutzbar.

Technische Mittel

  • Timeouts statt endlos warten
  • Retries mit Limits
  • Queues und asynchrone Verarbeitung
  • Health Checks, Monitoring, Alerting

Produktverhalten

  • Teilfunktionen dürfen ausfallen, Kernfunktion bleibt.
  • Fehler werden sichtbar und sauber behandelt.
  • Degradierter Betrieb ist besser als Totalausfall.
  • Recovery ist eingeplant, nicht improvisiert.

Beispiel für degradierte Funktion

Online-Shop: Das Empfehlungssystem ist down.

Schlechtes Design

  • Produktseite wartet auf Empfehlungen.
  • Nach Timeout lädt die ganze Seite nicht.
  • Ein Nebendienst blockiert den Verkauf.

Resilientes Design

  • Produktseite lädt ohne Empfehlungen.
  • Empfehlungsbereich zeigt Fallback oder bleibt leer.
  • Checkout und Warenkorb funktionieren weiter.

Ziel: Fehler isolieren, statt sie unkontrolliert durchs System zu verteilen.

Warum verteilte Transaktionen schwierig sind

  • Mehrere Services besitzen oft eigene Datenbanken.
  • Ein globales alles oder nichts über Servicegrenzen koppelt stark und ist betrieblich teuer.
  • Langsame oder nicht erreichbare Partner blockieren sonst das Gesamtsystem.
  • In Praxis häufig eventual consistency statt harte Sofort-Konsistenz über alles.
Beispiel Bestellung: Order-Service erstellt Bestellung, Payment-Service autorisiert Zahlung, Inventory-Service reserviert Bestand. Diese Schritte sind fachlich verbunden, technisch aber oft getrennt.

Event Sourcing

  • Der aktuelle Zustand wird nicht primär als letzte Tabellenzeile gespeichert.
  • Stattdessen werden fachliche Ereignisse gespeichert, z. B. OrderPlaced, PaymentAuthorized, OrderCancelled.
  • Der Zustand ergibt sich aus der Reihenfolge dieser Events.

Event Sourcing

Vorteile

  • Nachvollziehbarkeit
  • Read-Modelle können aus Events aufgebaut werden

Nachteile

  • Komplexeres Datenmodell
  • Versionierung von Events
  • Rebuilds und Konsistenzfragen

Zusammenspiel der Muster

Problem Typischer Ansatz Ziel
Antwort verloren, Aktion evtl. schon ausgeführt Retry + Idempotency Key Doppelte Wirkung vermeiden
Nebendienst fällt aus Timeout, Fallback Kernfunktion schützen
Fachliche Historie muss vollständig nachvollziehbar sein Event Sourcing Änderungen als Events speichern

Wann nicht über-engineeren?

  • Nicht jeder CRUD-Service braucht CQRS oder Event Sourcing.
  • Nicht jeder Fehler braucht aggressive Retries.
  • Idempotenz ist besonders wichtig bei fachlich teuren Aktionen: Geld, Bestellungen, Provisionierung, Webhooks.
  • Aktueller Industriestandard: erst Problem verstehen, dann das passende Muster gezielt einsetzen.

Merksätze

  1. In verteilten Systemen ist ein Timeout keine Seltenheit, sondern ein normaler Fall.
  2. Retries brauchen fast immer Regeln, Limits und oft Idempotenz.
  3. Resilience bedeutet nicht Fehlerfreiheit, sondern kontrolliertes Verhalten bei Fehlern.
  4. Über Servicegrenzen ist eventual consistency oft realistischer als globale Sofort-Transaktionen.
  5. Event Sourcing ist ein starkes Werkzeuge, aber nur dort sinnvoll, wo ihr Mehrwert die Komplexität rechtfertigt.
