Modul 321

Lektion 03: CQRS und Event Sourcing

Schreib- und Lesemodelle trennen, Fachereignisse speichern und Zustände nachvollziehbar aufbauen

Lernziele

  • Ich kann CQRS fachlich sauber erklären.
  • Ich kann Commands und Queries unterscheiden.
  • Ich kann erklären, warum Read-Model und Write-Model unterschiedlich aussehen dürfen.
  • Ich kann Event Sourcing detailliert erklären und mit Beispielen anwenden.
  • Ich kann beurteilen, wann CQRS und Event Sourcing sinnvoll sind und wann nicht.

Klassisches CRUD-Denken

Bei vielen Anwendungen greifen Schreiben und Lesen direkt auf dieselben Tabellen und dasselbe Datenmodell zu.

Einfach

  • Wenige Tabellen
  • Direkte SQL-Abfragen
  • Ein Datenmodell für alles

Skalierungsprobleme

  • Vermischen von Schreibregeln und Anzeigeanforderungen
  • Read- und Schreib-Queries belasten das selbe Modell.
  • Fachlogik, Historie usw. werden schwer trennbar.

CQRS

Command Query Responsibility Segregation trennt Zugriffe, die den Zustand ändern, von Zugriffen, die nur Informationen lesen.

Command

  • will eine Änderung auslösen
  • prüft Regeln und Invarianten
  • liefert meist Erfolg / Fehler zurück

Query

  • liest Daten
  • ändert keinen fachlichen Zustand

Was ist ein Command, was ist eine Query?

Beispiel Typ Begründung
ReserveSeat Command Der Zustand des Systems soll sich ändern.
GetSeatAvailability Query Es werden nur Daten gelesen.
CancelReservation Command Eine bestehende fachliche Tatsache wird verändert.
ListOpenInvoices Query Die Antwort dient nur der Ansicht oder Auswertung.

Die Kernidee von CQRS

Client
sendet Command oder Query
→
Write Side
validiert Fachregeln und speichert Änderungen
→
Read Side
liefert für die Anzeige optimierte Sichten

Die Trennung ist fachlich gemeint. Sie kann in einem Prozess, in einem Monolithen oder über mehrere Services umgesetzt werden.

Read- und Write-Model

Write-Model

  • fokussiert auf Konsistenzregeln
  • kleine, klare Aggregate
  • validiert Geschäftslogik

Read-Model

  • fokussiert auf schnelle Abfragen
  • darf Daten gezielt duplizieren
  • darf für UI oder Reports denormalisiert sein
Ein Dashboard braucht oft ganz andere Datenstrukturen als ein Command-Handler, der fachliche Regeln korrekt durchsetzen muss.

Beispiel: Kursanmeldung

Command-Seite

Schreibfall

  • EnrollStudent
  • Prüft: Kurs existiert, Platz frei, Frist offen
  • Speichert neue Anmeldung
Read-Seite

Lesefall

  • GetCourseOverview
  • Zeigt Titel, freie Plätze, Lehrperson, Teilnehmerzahl
  • Darf aus vorberechneter Sicht kommen

CQRS ist nicht automatisch Microservices

  • Ein modularer Monolith kann CQRS intern einsetzen.
  • Ein einzelner Service kann Commands und Queries logisch trennen.
  • Erst bei höherer Komplexität werden getrennte Deployments interessant.
Häufiger Irrtum: CQRS bedeutet nicht zwingend zwei Anwendungen, zwei Datenbanken. Es bedeutet eine Trennung der Verantwortungen.

Typische Vorteile von CQRS

Vorteil Nutzen in der Praxis
Klarere Fachlogik Write-Code muss nicht gleichzeitig Report-Logik bedienen.
Optimierte Read-Modelle Ansichten und Dashboards können schnell und einfach aufgebaut werden.
Skalierung nach Lastprofil Leseseite und Schreibseite können unterschiedlich wachsen.
Bessere Integration mit Events Read-Modelle können aus Änderungen oder Ereignissen gespeist werden.

Kosten und Fallstricke von CQRS

  • Zwei Modelle sind aufwändiger als eines.
  • Read-Seite kann zeitlich leicht hinterherhinken.
  • Debugging wird anspruchsvoller, weil mehr Teile zusammenspielen.
  • Für einfache CRUD-Systeme ist CQRS oft unnötige Komplexität.

CQRS lohnt sich dort, wo Lesebedarf, Fachlogik oder Skalierung wirklich auseinanderlaufen.

Event Sourcing

Statt nur den aktuellen Zustand zu speichern, speichert man die fachlich relevanten Ereignisse, die zu diesem Zustand geführt haben.

  • ReservationCreated
  • SeatAssigned
  • ReservationCancelled

Command, Event und Zustand sauber trennen

Command

Absicht oder Wunsch an das System.

Beispiel: PlaceOrder

Event

Eingetretene fachliche Tatsache.

Beispiel: OrderPlaced

Zustand

Ergebnis aus der Verarbeitung der Events.

Beispiel: Bestellung offen

Commands kann man ablehnen. Events nicht mehr: sie beschreiben etwas, das bereits passiert ist.

Wie Event Sourcing arbeitet

Command trifft ein
WithdrawMoney
→
Aggregate lädt Event-Stream und prüft Regeln
→
Neues Event wird gespeichert
MoneyWithdrawn

Beispiel: Bankkonto als Event-Stream

Reihenfolge Event Wirkung auf den Zustand
1 AccountOpened(0) Kontostand = 0
2 MoneyDeposited(200) Kontostand = 200
3 MoneyWithdrawn(50) Kontostand = 150
Der Zustand ist nicht primär gespeichert, sondern kann aus dem Event-Stream jederzeit wieder aufgebaut werden.

Replay: Zustand neu berechnen

Gedanklich

  1. Starte mit leerem Anfangszustand.
  2. Lies alle Events eines Aggregats in Reihenfolge.
  3. Wende jedes Event auf den Zustand an.
  4. Am Ende erhältst du den aktuellen Zustand.

Das ist nützlich für Debugging, Nachvollziehbarkeit, Recovery und den Neuaufbau von Projektionen.

Projektionen und Read-Modelle

Projection

  • liest Events
  • baut daraus eine Sicht auf
  • z. B. offene Rechnungen oder Tagesumsatz

Nutzen

  • neue Reports ohne Änderung am Write-Modell
  • unterschiedliche Sichten für UI, Suche und Reporting
  • Read-Modelle können gelöscht und neu aufgebaut werden

Snapshotting

Wenn ein Event-Stream sehr lang wird, kann man zwischendurch einen gespeicherten Zwischenzustand ablegen, damit nicht immer bei Event 1 begonnen werden muss.

  • Snapshot ist eine Optimierung, kein Ersatz für Events.
  • Danach werden nur noch spätere Events erneut angewendet.
  • Besonders relevant bei langlebigen Aggregaten.

Warum Event Sourcing attraktiv sein kann

Stärke Praxisnutzen
Vollständige Historie Fachliche Abläufe bleiben nachvollziehbar.
Auditierbarkeit Man sieht, welche Ereignisse zu welchem Zustand geführt haben.
Flexible Projektionen Neue Sichten können aus denselben Events entstehen.
Gute Passung zu CQRS Events speisen direkt unterschiedliche Read-Modelle.

Event Sourcing ist teuer

  • Das Modellieren guter Events braucht fachliche Disziplin.
  • Event-Versionierung und Schema-Änderungen werden wichtig.
  • Löschen oder Korrigieren ist heikler als bei einer einfachen Tabellenzeile.

Event Sourcing ist kein Speichertrick, sondern ein anderes Denkmodell.

Praxisbeispiel: Ticketverkauf

Command-Seite

  • ReserveTicket
  • Prüft, ob noch Plätze frei sind
  • Erzeugt TicketReserved
  • Später eventuell TicketPaid

Read-Seite

  • Übersicht freier Plätze pro Veranstaltung
  • Liste offener Reservierungen
  • Dashboard mit verkauften Tickets pro Tag

CQRS und Event Sourcing zusammen

Command
z. B. BookSeat
→
Event Store
z. B. SeatBooked
→
Projection / Read Model
z. B. freie Plätze pro Raum
Häufige Kombination, aber keine Pflicht: Man kann CQRS ohne Event Sourcing einsetzen und Event Sourcing auch ohne strikt getrennte Deployments nutzen.

Wann ist das sinnvoll?

Eher passend

  • komplexe Fachregeln
  • hoher Bedarf an Historie und Audit
  • viele unterschiedliche Read-Modelle

Eher unpassend

  • einfaches CRUD-Backoffice
  • kleines Team ohne Erfahrung
  • wenig Mehrwert durch Historie
  • hoher Zeitdruck bei sehr einfachem Problem

Typische Fehlerbilder

  • Commands und Events gleich benennen und fachlich vermischen.
  • Read-Modelle wie die einzige Wahrheit behandeln.
  • Jede kleine CRUD-Tabelle zwanghaft event-sourced bauen.
  • Zu technische Events statt fachlich verständlicher Ereignisse modellieren.

Merksätze

  1. Ein Command will ändern, eine Query nur lesen.
  2. CQRS trennt Verantwortungen, nicht zwingend Deployments.
  3. Event Sourcing speichert fachliche Ereignisse statt nur Endzustände.
  4. Read-Modelle dürfen aus Events neu aufgebaut werden.

Mini-Check

Warum darf ein Read-Model bewusst anders strukturiert sein als das Write-Model?

Unterschiedliche Ziele: Das Write-Model soll Fachregeln und Konsistenz korrekt abbilden, das Read-Model soll Abfragen für UI, Suche oder Reports möglichst einfach und schnell liefern.

Mini-Check

Worin liegt der Unterschied zwischen PlaceOrder und OrderPlaced?

PlaceOrder ist ein Command, also die Aufforderung oder Absicht, eine Bestellung zu erfassen. OrderPlaced ist ein Event, also die fachliche Tatsache, dass die Bestellung bereits erfolgreich erfasst wurde.

Mini-Check

Weshalb ist Event Sourcing für Audit und Historie besonders interessant?

Weil nicht nur der aktuelle Zustand gespeichert wird, sondern die vollständige Folge fachlicher Ereignisse. Dadurch bleibt nachvollziehbar, wann was passiert ist, wie ein Zustand entstanden ist und welche Änderungen im Zeitverlauf stattgefunden haben.
